# Java 工程师专属：AI 概念与心智模型速查字典

> **核心法则**：不要把大模型看成神秘的黑盒，它在计算机底层的本质就是一个庞大的**矩阵计算流水线**。以下是 AI 常见黑话与 Java 经典概念的 1:1 对照。

---

## 一、 数据结构与表示篇

| AI / 算法术语 | 纯 Java 数据结构对照 | 人话解释与直观比喻 |
| :--- | :--- | :--- |
| **标量 (Scalar)** | `float` 或 `int` | 一个单独的数字（0 维）。例如某个词的得分 `3.14f`。 |
| **向量 (Vector / Embedding)** | `float[]` | 一行数字（1 维数组）。计算机看不懂汉字，用一个长度为 $D$（如 1600）的浮点数数组作为该词的“数字特征身份证”。 |
| **矩阵 (Matrix)** | `float[][]` | 二维表格（Excel 表格）。行代表条目（如序列里的不同词），列代表特征。 |
| **张量 (Tensor)** | `float[][][]`（3维或更高维） | 多维数组。在推理时最典型的形状是 `float[B][S][D]`：<br>• `B`（Batch）：一次并发处理几个用户的请求；<br>• `S`（SeqLen）：一句话切成了几个 Token（词）；<br>• `D`（Dimension）：每个词的特征数组长度。 |
| **Embedding 表** | `float[vocab_size][d_model]` | 静态词典大表。输入一个词的整数 ID（如 42），直接从数组下标取出对应的 `float[]` 初始特征向量（纯查表，无上下文）。 |
| **词表 (Vocab)** | `Map<String, Integer>` / `String[]` | 字典映射。把切分后的 Token 映射为唯一的数字编号 ID。 |
| **Token 与 BPE** | 字节级贪心压缩算法 | 大模型不认“字符”，而是按 UTF-8 字节（0~255）根据语料库高频相邻出现的频率，合并成的新词块。数字、中文、空格的切分边界均由此决定。 |

## 二、 计算与网络层（Layers）篇

| AI / 算法术语 | 纯 Java 运算 / 架构对照 | 人话解释与直观比喻 |
| :--- | :--- | :--- |
| **点积 (Dot Product)** | `for(int i=0; i<n; i++) sum += a[i]*b[i];` | **相似度打分器**。两个特征数组对应项相乘再累加。几何意义是夹角余弦，乘积越大代表两个词越匹配、越相关。 |
| **Linear (线性层 / 仿射变换)** | 矩阵乘法 `y = x @ W.T` | 每个词关起门来，用一组固定的权重矩阵 $W$ 对自己的特征数组做加权求和与升降维，等价于一个强力类型转换器。 |
| **Attention (注意力机制)** | **双重循环全员开会交流** | 句子里所有词两两计算点积，算出每个词该关注上下文里的哪些词，并把对方的信息按权重吸收到自己身上。复杂度为 $O(S^2)$。 |
| **FFN / SwiGLU (前馈层)** | `tokens.parallelStream().map(...)` | **回工位各自消化**。开完会后，每个词拿到了新线索，各自独立通过非线性门控函数加工自己的向量，词与词之间互不干扰。复杂度为 $O(S)$。 |
| **Logits** | 原始无界打分数组 `float[vocab_size]` | 模型跑完所有层后，给词表里每个候选词打出的原始分，有正有负，无法直接当概率。 |
| **Softmax** | 归一化百分比转换函数 | 先对 Logits 做指数计算（$e^x$）拉大优胜者差距，再除以总和，变成总和为 100% 的概率分布。 |
| **Temperature (采样温度)** | Softmax 前的除法因子：`logits[i] / T` | 调 API 必备参数。$T \to 0$ 拉大最高分差距（极度确定，适合写代码/调工具）；$T > 1$ 抹平差距（增加随机性发散思维）。 |
| **RMSNorm** | 数组音量稳定器 | 防止高维浮点数在几十层矩阵运算中越乘越大导致数值溢出，按均方根进行归一化。在 Java 里类似对信号做限幅滤波。 |
| **Causal Mask (因果遮罩)** | 下三角矩阵拦截器 | 防止穿越。保证算 Attention 时，前面的词只能看自己和过去，绝对看不到未来的词。这就是 Decoder-only 自回归的基础。 |

## 三、 推理生命周期与系统架构篇

| AI 概念 | Java 微服务 / 并发模型对照 | 生产实践痛点 |
| :--- | :--- | :--- |
| **Prefill (预填充阶段)** | **并行批处理流水线** | 用户输入的 Prompt 包含的所有 Token，一次性拼成矩阵扔进 GPU 满载并行计算完毕。计算量大但充分利用算力。 |
| **Decode (解码生成阶段)** | **单线程串行 自回归 `while` 循环** | 模型吐字是一个字一个字循环生成的。每吐一个词，都要把这个词拼回输入，重新读一遍几十 GB 的显存权重。因此**输出 Token 比输入 Token 慢得多、贵得多**。 |
| **KV Cache** | **状态空间换时间（LRU/分页内存池）** | 在 Decode 循环中，过去的词算出来的 Key/Value 矩阵是不会变的，把它们缓存进显存，避免每次生成新词都要重算前面所有词的 Attention。类似 Java 堆外内存池。 |
| **Prefix Caching** | **公共前缀树缓存（Radix Tree）** | 多个请求如果共享相同的 System Prompt 或长文档前缀，服务端直接复用已算好的 KV Cache，实现 **TTFT 首字延迟立减 80% + 费用打折**。 |
| **TTFT (Time To First Token)** | **首包延迟 / 首字节到达时间** | 从后端发起请求到拿到大模型 SSE 流式推送的第一个字的时间，直接受 Prefill 阶段长上下文 $O(S^2)$ 算力影响。 |
