# 教学示范：什么样的故事算好，一轮好的讲解长什么样

> 规则说「先讲故事，再落到术语」，但没说什么样的故事才算好。本文件用一次真实的教学经历（讲解 BPE 分词，学习者为 Java 后端、DL/NLP 零基础）给出标准与正反示范。讲课前先读本文件，对照着讲。

---

## 〇、学方法，不抄场景

本文件的示范都来自同一个主题（BPE），场景是「只认数字的同事 + 密码本」。**这个场景只适合 BPE，不要套到其他主题上。**

| ✅ 该学的（换任何主题都适用） | ❌ 不该照搬的（只属于这一次） |
| :--- | :--- |
| 六条好故事标准 | 「同事 + 密码本」这个场景 |
| 一轮讲解的节奏：一个场景、一个问题、落到术语、说清先不管什么、一道练习 | 「翻聊天记录、手数」这类具体素材 |
| 纠错要演算、推翻简化要明说、数值先实测、收尾用术语复述 | 回复的长度、措辞和开场白（如「刚才讲得太快」只适用于重讲） |

### 怎么为新主题找场景

1. **先找动机**：这个概念解决了什么痛点？没有它会怎样？（BPE 的动机是「每个字发一个号码太浪费」。）
2. **再找同构场景**：找一个学习者熟悉、结构相同的场景，让痛点在场景里自然出现。学习者是后端工程师时，工程场景（缓存、连接池、消息队列、数据库索引）往往比生活场景更贴切。
3. **最后检验**：把这个主题的术语列出来，每一个都要能在场景里指出对应物。指不出来，或者需要硬凑，就换场景。
4. **不适合手算的概念不要硬凑手算**：可以换成能画出来的小图或几行能跑的代码，原则仍是「规模小到学习者能自己看懂」。

## 一、好故事的六条标准

### 1. 一个主题只用一个连贯场景，所有术语都是场景里的角色、道具或动作

| ❌ 差 | ✅ 好 |
| :--- | :--- |
| 一个概念配一个比喻：BPE 像压缩包、Token 像乐高积木、Embedding 像坐标、词表像字典……比喻之间互不相干，比喻本身也要记 | 整个主题只有一个场景：「你有一个**只认数字的同事**，你们共用一本**密码本**」。之后的所有术语都挂在这个场景上 |

判断方法：把术语列出来，每一个都能在场景里指出对应物。

| 术语 | 场景里的对应物 |
| :--- | :--- |
| 模型 | 只认数字的同事 |
| 词表 / 分词器 | 密码本 |
| Token / Token ID | 一块 / 号码 |
| 合并 merge | 粘块 |
| 合并顺序 rank | 粘块的先后顺序 |
| 嵌入表 Embedding | 同事手里的员工档案表 |

### 2. 先讲动机：为什么要这么做

| ❌ 差 | ✅ 好 |
| :--- | :--- |
| 「BPE 从字符开始，反复合并最高频的相邻对……」直接讲步骤 | 「你天天说『收到』，每次都要发两个号码，很浪费。那就给常用的词单独发一个号码。**哪些词值得单独发号码？**这就是 BPE 要解决的问题。」 |

没有动机，记住的只是「怎么做」，过一段时间就会忘了「为什么」。

### 3. 用学习者的母语和日常素材，规模小到能手算

| ❌ 差 | ✅ 好 |
| :--- | :--- |
| 英文语料 `hug ×10, pug ×5, pun ×12, bun ×4, hugs ×5`，要乘词频、数 6 种相邻对 | 4 句聊天记录：`收到`、`收到了`、`好的`、`好的收到`，一眼能数出「收到」出现 3 次 |

数字越少越好，学习者要能自己在脑子里算出来。

### 4. 场景能延伸，后面的概念不用换场景

后续概念出现时，在同一个场景里加道具，而不是另起一个比喻：

- 讲到 Embedding：同事收到号码后，去翻**员工档案表**，号码就是工号，档案是 4096 个小数；
- 讲到字节：密码本最底下一层是 **8 个开关**组成的字节，一共 256 种，一开始就全收进去了；
- 讲到换分词器：把 A 的密码本给 B 用，B 去翻自己档案表的第 7 行，拿到的是别人的档案。

### 5. 主动说出类比在哪里不成立

> 「它有点像输入法把常打的词组升级成整词。**不同的是**，BPE 的合并完全由统计决定，而且会合并出『半个汉字』这种不完整的块，单独显示是乱码。」

点出边界，说明这是在讲机制，不是在背比喻。

### 6. 学习时用生活场景，面试时换成工程类比

生活场景（同事、密码本）用于第一次理解。面试官是工程师，面试口径里换成工程类比，既好懂又显专业：

- 词表就是 `Map<String, Integer>`；
- 查嵌入表就是 `embedding[id]`，按下标取数组的一行；
- 把 A 的分词器给 B 用，相当于 `ArrayIndexOutOfBoundsException`。

## 二、一轮讲解：差的一轮 vs 好的一轮

### ❌ 差的一轮（学习者反馈：完全没明白）

学习者问「BPE 细细讲讲」，一条回复里同时给出：

1. 一张 10 行的「API 参数与 Token 关系」表；
2. 「为什么需要子词」的三方案对比表；
3. 英文语料 hug/pug/pun 的 4 轮手算；
4. 训练和编码两段 Java 代码；
5. 字节级 BPE、UTF-8、SSE 乱码的两个来源；
6. 三个面试后果和一张面试卡；
7. 末尾两道练习。

问题：每一部分单独看都对，但一次塞了七个主题，术语密度极高，学习者找不到主线。

### ✅ 好的一轮（重讲后学习者能跟上并开始追问）

结构：**承认上一轮讲多了 → 一个场景 → 一个问题 → 手算 → 落到真实系统 → 说清先不管什么 → 一道练习**。

> 刚才讲得太快、术语太多，从头来，这次只讲一件事。
>
> **想象一个场景**：你有一个同事，他只看得懂数字。你们共用一本密码本：`收=1 到=2 了=3 好=4 的=5`。发「好的收到了」要发 `4 5 1 2 3`，5 个号码。大模型就是这个同事，**这本密码本就叫分词器（Tokenizer）**。
>
> **问题来了**：你天天说「收到」「好的」，每次发两个号码很浪费。给常用词单独发号码 `收到=6 好的=7`，就只要发 `7 6 3`。**哪些词值得单独发号码？**
>
> **BPE 的办法：翻聊天记录，数数。**（4 句聊天记录，数出「收到」3 次最多 → 粘成一块，**这一步叫合并 merge** → 再数一遍，「好的」2 次 → 再粘。）**这就是 BPE 的全部。**
>
> **和真实模型的关系**：厂商翻的是几百 GB 文章，粘十万次左右，每一块就叫 **Token**。
>
> 字节、乱码、代码先不管，后面再说。
>
> **小练习**：用这本密码本，「收到了好的」切成哪几块？发几个号码？

要点：
- 每引入一个术语，紧跟在故事动作后面点名（「这本密码本就叫分词器」「这一步叫合并 merge」）；
- 明确说「X 先不管」，减轻学习者的负担；
- 练习只考这一轮讲的内容。

## 三、单项示范

### 1. 学习者说「完全没明白」：整个推倒重讲

不要在原讲法上补充解释或追加例子，而是承认讲多了，换一个更简单的场景从头讲，并且只讲一件事（见上面「好的一轮」）。

### 2. 练习纠错：演算出来，指出错在哪条规则

学习者答「好收到的」切成 2 块（误以为不相邻也能合并）：

> 不对。「好的」只有在「好」和「的」**紧挨着**时才能粘：
>
> ```
> 好 收 到 的
> 第 1 条规则「收到」先执行 → 好 [收到] 的
> 第 2 条规则「好的」：好 和 的 中间隔着 [收到]，不挨着 → 粘不了
> 结果：好 / 收到 / 的 → 3 块
> ```
>
> 规则只粘相邻的两块，隔开了就不行。

### 3. 推翻前面的简化：明说，并在同一个场景里延伸

> **先修正上一轮的一个简化**：上一轮为了好懂，我们假装密码本的最小单位是「字」。实际上「收」本身也是粘出来的，它由更小的东西粘成，这个更小的东西叫**字节**。

然后沿用密码本场景，加一层「8 个开关」，不换比喻。

### 4. 数值先实测再讲

讲字节时，先在本机运行：

```python
for ch in ["A", "收", "龘", "😂"]:
    b = ch.encode("utf-8"); print(ch, len(b), list(b))
```

再把实测结果（「收」= 230, 148, 182）讲给学习者。实测中暴露的细节本身就是好素材：Java 的 `"收".getBytes(UTF_8)` 打印为 `[-26, -108, -74]`，因为 `byte` 有符号，要用 `& 0xFF` 转回 0～255。

### 5. 收尾：用术语复述，故事放在后面

请学习者用术语讲一遍 30 秒口径，标准顺序是**结论 → 机制 → 工程类比 → 类比边界 → 工程后果**：

> 「BPE 是一种**字节级的子词合并算法**。训练时从 256 个字节值出发，反复统计相邻 pair 的频次，把最高频的一对**合并**成新 Token，合并顺序记为 **rank**。工程上看，词表就是一个 `Map<String, Integer>`，编码就是按 rank 做确定性合并再查表。它有点像输入法把常打的词组升级成整词，**不同的是**合并完全由统计驱动，还会产生半个汉字这样的不完整 Token。所以同一句中文在不同模型里 Token 数不同。」

学习者说不出某个术语时，用场景里的叫法提示（「粘块那一步叫什么？」），而不是直接告诉答案。

### 6. 出题：考概念，不考某个模型的具体数字

| ❌ 差 | ✅ 好 |
| :--- | :--- |
| 「Llama 3 8B 里一个 Token 的档案有几格？名牌有几格？缩放除以多少？」——考的是记不记得 4096、128，换个模型就作废，学习者也看不出这道题想练什么 | 「档案长 6，Wq 和 Wk 都是 4 行 × 6 列。缩放时除以 √6 还是 √4？为什么？」——直接考「缩放看名牌长度 dk，不看档案长度」，顺带复习翻译器形状 |

出题前先问自己：**这道题想让学习者分清的是哪个概念？** 把那个概念放到题目正中，用小到能手算的数字。具体模型的配置可以在讲解里作为「真实世界长这样」的佐证出现，但不要拿来出题。

题目要有「为什么」：只问结果，学习者可能蒙对或套错公式也得出对的数（如用给定的指数值直接算出百分比，却没发现缩放那一步除错了）。

### 7. 为手算做简化时，当场说清省略了什么

为了能手算，例子常常只取一部分：只让一个词比对其中几个人，或者不画出它自己。省略本身没问题，**问题是不说**。学习者会把例子当成规则本身，以后很难纠正。

| ❌ 差 | ✅ 好 |
| :--- | :--- |
| 只列出冰箱、蛋糕、放进三个人的名牌就开始算，几轮后出现「3 个人的话被压成一份」，学习者问：句子明明 8 个词，3 个人是哪来的？ | 「为了能手算，只取前面 3 个人示意；真实计算中『满了』会和自己加前面 7 个人，一共 8 个人打分。」 |
| 说「拿需求单对每个人的名牌打分」，但例子里只画别人。学习者记成「Query 只和其他 Token 的 Key 打分」，后来做 softmax 时把自己从分母里漏掉 | 例子里也画出自己的名牌，或明说「这里没画自己，真实计算包括自己」 |

做法：每次为了手算删掉一部分，就用一句话说出**删了什么、真实情况是什么**。已经写进知识卡片的简化，同样要在卡片里注明。

同一类问题还有：例子用「一个词一个 Token」，要说明真实切法由分词器决定；例子用 2 格向量，要说明真实是几千格；给格子起名字（「能装东西」「是动作」），要说明真实模型的格子没有人能读懂的含义。

### 8. 下标统一从 0 开始，不混用「第 N 个」

公式和代码里的下标都从 0 开始（格下标、指针下标 i、位置 pos）。讲解时只说下标，不说日常的「第 N 个」。两种数法一混用，学习者代入公式时就会差一位。

| ❌ 差 | ✅ 好 |
| :--- | :--- |
| 讲正弦编码时说「格 0、格 1」，讲 RoPE 时又说「第 1 格、第 2 格」；同一题里既说「格 4 属于第 3 根指针」，又写 i = 2。学习者代入公式时用了 i = 3，指数算成 0.75（正确为 0.5） | 始终说「格 4 属于指针 i = 2」，公式也按下标写：`新格 2i = 格 2i·cos t − 格 2i+1·sin t`，与课程原文的 `q'_2i` 对得上 |

例子为了好懂从 1 开始数（如座位 1、2、3）时，当场说明「代码从 0 开始，不影响道理」。
