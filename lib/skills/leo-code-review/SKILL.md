# Leo Code Review (高信噪比本地代码与 AI 改动审查中枢)

A lean, cross-tool, low-noise code review skill for reviewing local git modifications before commit. Built specifically for inspecting code generated by other AI agents with an extensible router architecture.

---

## 1. Core Principles (核心审查原则)

1. **Multi-Track Audit (多轨审查)**:
   - **Track A (Runtime & Logic Bugs)**: Logic inversions, null safety, off-by-one, race conditions, resource leaks, silent exception swallows.
   - **Track B (Agent Spec Compliance)**: Guarding against AI shortcuts—unimplemented `TODO` stubs, requirement drift, dropped corner cases, broken existing contracts, and phantom APIs (see [agent-work-inspection.md](references/agent-work-inspection.md)).
   - **Track C (Domain Architectural Compliance)**: For specific tech stacks (e.g. Java), hooks domain guidelines like `leo-coding-standards` to intercept production-critical architectural violations (`MUST` level) while suppressing style nitpicks.
2. **Extreme Signal-to-Noise (极低噪音)**:
   - Absolute ban on formatting, style nitpicks, linter-catchable issues, and ungrounded guesses (see [false-positive-rules.md](references/false-positive-rules.md)).
3. **Strict 0–100 Confidence Cutoff (80 分硬截断)**:
   - Every candidate issue is scored. Any issue scoring **< 80 points is silently dropped**.
4. **Two-Stage Falsification Isolation (两阶段独立证伪)**:
   - Finding an issue is not enough; the reviewer must actively try to **disprove** it using the **latest full workspace files**.
5. **Zero-Issue Silence Rule (零问题闭嘴原则)**:
   - If no issue satisfies the $\ge 80$ confidence bar, output exactly one clean confirmation line. **Never invent nitpicks to pad the response**.

## 2. Extensible Router Architecture (可扩展架构)

To maintain a lean core, `leo-code-review` delegates specialized knowledge to modular references and external skills:

```
leo-code-review (Orchestrator)
├── Stage 0: Context & Diff Ingestion (scripts/git_diff_extractor.py)
├── Stage 1: Candidate Discovery
│   ├── General Bug Principles (references/false-positive-rules.md)
│   ├── AI Agent Anti-Stub / Spec Audit (references/agent-work-inspection.md)
│   └── [Optional Router Hook] Domain Skills (e.g. leo-coding-standards for Java)
├── Stage 2: Independent Falsification Loop (Devil's Advocate verification)
└── Stage 3: Chinese Output Generation (references/output-format.md)
```

- **Adding Custom Rules**: Place specialized checklists in `references/` (e.g. `references/security-audit.md`, `references/python-rules.md`).
- **Connecting Upstream/Downstream Routers**: When specific file types (e.g., Java `.java`, Vue `.vue`) or project rules are detected, read corresponding companion skill guidelines without bloating this orchestrator.

## 3. Step-by-Step Execution Workflow (执行流水线)

### Stage 0: Ingest Diff & Context (获取改动与意图)
1. **Extract Git Changes**:
   - Python environment is pinned to `~/.shrimp/skills/leo-code-review/.venv`.
   - Run the extractor via `uv`:
     - **macOS / Linux**:
       ```bash
       uv run --python "$HOME/.shrimp/skills/leo-code-review/.venv" "<skill-dir>/scripts/git_diff_extractor.py"
       ```
     - **Windows PowerShell**:
       ```powershell
       uv run --python "$HOME\.shrimp\skills\leo-code-review\.venv" "<skill-dir>\scripts\git_diff_extractor.py"
       ```
   - *Direct Git fallback (if uv is temporarily unavailable)*:
     Execute `git diff HEAD`, fallback to `git diff main...HEAD` if clean; collect untracked files via `git status --porcelain -uall`.
   - If no git changes exist in the workspace, immediately output: `✅ 工作区干净，无待审查的代码改动。` and terminate.
2. **Extract User Requirement / Task Context**:
   - Retrieve the user's initial prompt or latest task requirement in the current conversation. This serves as the source of truth for **Track B (Spec Compliance)**.
3. **Optional Project Instruction Scan**:
   - Check if `AGENTS.md`, `CLAUDE.md`, or `.cursor/rules` exist in the repo root. If present, briefly note explicit constraints; do NOT launch dedicated subagents.

---

### Stage 1: Primary Discovery (候选问题初筛)
Inspect the unified diff and newly added files across three focused tracks:
- **Track A (Bugs)**: Look for reachable crashes, inverted conditions, concurrency races, resource leaks, or empty catch blocks.
  - *Constraint*: Every proposed bug MUST identify a concrete triggering input, state, or interleaving sequence. Vague speculations are discarded.
- **Track B (AI Agent Compliance)**: Consult [agent-work-inspection.md](references/agent-work-inspection.md).
  - Did the code skip any requirement requested by the user?
  - Are there placeholder stubs (`TODO`, `FIXME`, dummy returns, empty mocks) falsely presented as complete?
  - Did the agent inadvertently break existing public interfaces or perform unprompted mass refactorings?
- **Track C (Domain Architectural Compliance - e.g. Java)**:
  - If `.java` files are touched, consult `leo-coding-standards/references/review-checklist.md` for `MUST`-level red lines:
    1. **DDL & DB constraint**: Columns must be `NOT NULL DEFAULT ...`; strict ban on physical `UNIQUE` indexes.
    2. **Apollo config**: `@Value("${key:default}")` must provide fallback default values; complex JSON must use `@ApolloJsonValue` with fallback.
    3. **Spring Bean DI**: Only field injection (`@Autowired` / `@Resource`) is permitted; strict ban on constructor injection or Lombok `@RequiredArgsConstructor` / `@AllArgsConstructor`.
    4. **Critical Path Logs**: Core business entrypoints (interfaces, RPC, MQ consumer, scheduled tasks) and state transitions must have `INFO` logs with stable business IDs and context.
    5. **Historical Class Appending**: In existing classes, new methods/code must append at the bottom of class definitions to avoid interleaving disruption.
  - *Constraint*: Only flag explicit violations of `MUST` constraints. Style recommendations (`SHOULD` / `CONSIDER`) are suppressed to maintain high signal-to-noise.

*Assign each candidate an initial confidence score (0–100).*

---

### Stage 2: Independent Falsification (独立反方证伪)

Before presenting any issue to the user, conduct a rigorous **Devil's Advocate** falsification step:

1. **Read Full Context (No Diff Hallucinations)**:
   - For every candidate line, read the **actual full workspace file** around that function.
   - Check callers, type definitions, guard clauses, default fallback parameters, or global interceptors.
2. **Attempt to Disprove**:
   - Try actively to prove the candidate is a false positive. (e.g., "Is the variable already validated upstream? Is this exception handled by a parent boundary?").
3. **Token Conservation & Concurrency Strategy**:
   - **If Subagent is available**: Invoke **one single independent subagent** with a fresh context, providing the candidate issues and asking it to critically falsify them against the latest files.
   - **If Subagent is unavailable (Single-session fallback)**: Execute an explicit, self-contained **Devil's Advocate** reasoning step in the current session.
4. **Hard Score Cutoff**:
   - Re-evaluate score. Any issue falling below **80 points** is silently eliminated.

---

### Stage 3: Chinese Output Generation (中文报告输出)

Format the final response strictly according to [output-format.md](references/output-format.md):

- **If 0 issues pass the 80-point bar**:
  ```markdown
  ✅ 未发现高置信度缺陷与需求偏差。（已对本地改动进行高信噪比 Bug 审查与需求一致性核验）
  ```
- **If $\ge 1$ issues confirmed**:
  Sort by severity (P0 致命 $\rightarrow$ P1 高危 $\rightarrow$ P2 隐患), displaying:
  - `[置信度: XX/100] 【级别】 文件路径:行号 — 一句话简述`
  - **类别**：功能逻辑漏洞 / 需求实现偏差 / 架构规范违规 / 静默异常吞咽 / 虚假桩实现
  - **触发路径 / 偏差证据**：具体复现状态、参数或需求矛盾对照
  - **最小修复**：精简、准确的代码补丁建议
