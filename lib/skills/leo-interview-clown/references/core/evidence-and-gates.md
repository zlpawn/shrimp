# 证据分级、覆盖台账与质量门禁

所有模式（`doc`、`repo`、`method`、`hybrid`）共用本规范。完备性与诚实性是**发布硬门禁**，不是可选项。

## 1. 证据标签体系

每条关键（load-bearing）结论必须标注以下标签之一：

| 标签 | 含义 | 能否作为当前事实陈述？ |
|---|---|---|
| `直接证实` | 源码、SQL、Schema、生效配置、测试或一手基准直接证明 | 可以（限定在已观测范围内） |
| `原文声明` | 外部文章、README、设计文档、论文明确声称，但尚未独立实证 | 仅作为原文主张（`source-claimed`）陈述 |
| `用户确认` | 用户补充的业务背景、生产指标、个人分工或运行态事实 | 可以（注明来源为用户确认） |
| `知识化综合` | 跨章节或跨模块综合多个已证实事实得出的结构化总结 | 可以（标明为综合归纳） |
| `工程评估` | Agent 对合理性、缺失条件、风险、边界或重做方案的判断 | 严禁归因给原作者或原项目 |
| `交叉推断` | 基于多条间接代码/文档线索推理得出 | 必须显式标为推断 |
| `发现冲突` | 代码、文档、图表、表格或模块之间存在矛盾 | 不可猜测选边；必须并列呈现双方证据 |
| `待确认` | 证据缺失，或依赖未观测的运行时/业务策略 | 不可作为事实；列入待确认清单 |

## 2. 四层严格隔离原则

针对每个核心机制或难点，必须把以下四件事拆开写，严禁混淆：
1. **当前实现 / 原文主张**：现在代码或资料里实际写了什么。
2. **可验证的效果**：该实现或实验能确切保证什么。
3. **已知缺口或未知边界**：当前证据无法确认或尚未覆盖的部分。
4. **改进设想**：如果重做可以怎么优化（绝不允许用改进设想反向脑补当前系统的能力）。

## 3. 禁止静默脑补清单

- 原始设计意图、历史取舍理由或“曾经考虑过的备选方案”（除非 ADR/文档证实或用户确认；否则备选方案只能作为分析对比呈现）。
- 生产指标（QPS、P99 延迟、数据量、机器数、成本节省、业务收益百分比）——仅接受用户确认、监控/压测报告、生产配置直推或可复现计算；缺失时输出**“待收集数字清单”**，绝不填示例数值冒充真实数据。
- 个人贡献归属（“我设计/我实现”）。
- 休眠配置或未挂载代码在生产环境是否真正启用。
- 仅靠周围正文去猜一张未读取图片的内容。

## 4. 覆盖台账规范

### 文档 / 混合模式（`Section / Claim / Media Ledger`）
在 `<run-dir>/extraction/` 中维护完整覆盖台账：
- **章节台账（`section-ledger.yaml`）**：记录每个原文章节、代码块、附录、嵌入资源；标注 `importance`（`load-bearing` | `supporting` | `contextual`）、`read_status`（`complete` | `partial` | `unreadable`）、`disposition`（`curated` | `source-only` | `blocked` | `uncertain`）与 `destinations`。
- **主张台账（`claim-ledger.yaml`）**：重点跟踪核心主张与指标，保留指标成立的 **8 项实验/运行条件**：数据集、时间窗口、负载特征、对比基线、硬件规格、并发度、分位数口径、测量方式；条件缺失必须显式点出。
- **媒体台账（`media-manifest.yaml`）**：记录每张图/白板/附件的来源锚点、原图 URL/文件、本地副本、重要性（`load-bearing` | `supporting` | `decorative`）、读取状态与理解置信度。

### 代码模式（`Area & Flow Ledger`）
盘点所有模块、入口、数据锚点、定时任务、MQ 消费者、回调、外部调用与测试：
- 状态取值：`deep`（已业务+代码双深挖）| `surveyed`（已盘点定性）| `partial`（重要但未追全）| `excluded`（明确排除及理由）| `unresolved`（关系尚待明确）。
- 角色取值：`core-candidate` | `supporting` | `infrastructure` | `generated` | `deprecated-looking` | `unresolved`。
- **核心候选多维信号**：业务价值、生命周期控制力、数据中心性、编排中心性、故障影响面、项目特异性。严禁仅凭代码量大、技术时髦或面试好讲就将某模块判定为核心。

## 5. 视觉门禁（图片 / 架构图 / 白板 / 截图）

所有出现“如下图所示”的图片默认视作 `load-bearing`，直到完成视觉检查。

每张 `load-bearing` 图片必须给出 **3–6 条专业解读**，覆盖适用维度：
- 该图回答的核心问题与设计意图
- 图中的组件、分层或参与方
- 数据流向、控制流箭头、状态迁移或依赖方向
- 坐标轴、图例、指标单位或实验条件
- 图中存在但正文未文字说明的信息
- 模糊、截断、冲突或无法辨认的区域

**交叉验证**：逐项核对正文、表格、代码与图表在组件名称、流转方向、数字单位与边界条件上是否一致，有冲突如实暴露。

## 6. 阻塞规则

- 任何 `load-bearing` 章节或 `load-bearing` 图片无法完整读取 → 提案状态标为 **`BLOCKED`**，写明缺什么权限或文件，**禁止进入 Phase 2 发布**。
- `load-bearing` 证据仅部分可读 → 默认阻塞，除非缺失部分可被明确证明非关键。
- `supporting` 或 `decorative` 内容无法读取 → 可继续，但必须在缺口清单中写明。

## 7. 反向完备性审计（Phase 2 发布前必检）

发布前逐条核验：
- **文档/混合**：所有章节与媒体均已录入覆盖矩阵；所有 `load-bearing` 章节已进入精炼知识；每张 `load-bearing` 图均有本地原图（或批准的例外）及 3–6 条解读。
- **代码/混合**：所有业务入口均已映射主流程或说明排除理由；核心数据锚点的创建、读取、变更与终态齐全；关键状态机覆盖进入/退出/恢复路径；外部依赖标明用途与失败影响；调度/消费/回调/补偿/人工入口均有业务角色；成功、重试、超时、取消、人工修复路径均已核查。
- **全局一致性**：图表、正文与代码/原文证据一致；改进设想未被写成现状；指标与个人贡献无编造；已发布页面无断链、无失效图片路径、无残留的 `~/.shrimp/.../runs/` 临时路径。

任意一项未通过则记录 `fail`（或如实标为 `partial` 并列出未核实范围），且**保留运行目录供排查，禁止清理**。
