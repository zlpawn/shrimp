# 输出页面角色与知识库适配规范

根据材料体量与目标知识库规范灵活组织页面数量与角色，不机械套用空章节，也不强行拆出碎页面。

## 1. 可选页面角色

| 角色 | 适用场景 |
|---|---|
| `project-mastery` | 整仓或子服务的深度内化档案 + 面试话术 + 追问防御（如 `projects/<repo>/PROJECT_MASTERY.md`） |
| `method-mastery` | 单方法/接口/Consumer/Job 的局部追踪与五层解析（如 `methods/<symbol>/METHOD_MASTERY.md`） |
| `system` | 端到端系统/架构文章的因果内化与面试讲解页（如 `docs/<topic>/...`） |
| `concept` | 独立于单个来源的可复用核心机制或原理页 |
| `method` | 可复用的工程方法、排查流程或评测方法页 |
| `query` | 高频面试/工程问题及其综合解答页 |
| `comparison` | 明确维度、指标条件与适用边界的技术方案对比页 |
| `source` | 完整源文档快照、元信息、源锚点与本地高清媒体归档 |

## 2. 外部知识库的代码锚点与拆分规范

- **跨目录锚点防断链**：当档案落盘在独立知识库（如 Obsidian 或 `~/.shrimp/skills/leo-interview-clown/output/`）而非源码仓库内部时，**禁止生成会断链的相对路径**（如 `[OrderService.java](src/OrderService.java#L42)`），也不要默认输出 `file:///` 链接。统一使用 **`仓库名 :: 相对路径:行号`**（可附 commit/分支）：
  - 示例：`` `order-service :: src/main/java/.../OrderService.java:L42-L88` ``
- **超大仓库拆分**：单文件过长不利于复习时，可在目标目录按模块拆分为：
  ```text
  <target>/<project_subdir>/<repo>/
  ├── PROJECT_MASTERY.md   # 核心认知模型、全景流、难点卡与面试口述
  ├── CODE_EVIDENCE.md     # 完整覆盖账本、数据/状态锚点与代码证据地图
  ├── INTERVIEW_QA.md      # 分层追问树、三轮自测题与掌握度地图
  └── diagram/             # （可选）渲染后的架构/状态图
  ```

## 3. 通用深度内化档案模板

根据模式裁剪（`method` 模式省略整仓视角章节；`doc` 模式按 `system`/`concept` 组织正文并保留末尾面试武器库）：

```markdown
# <项目/系统/方法/专题名称> 深度内化档案

> 分析模式：[doc | repo | method | hybrid]  
> 分析状态：[complete | partial]  
> 来源与版本：[<URL/文档标识> 或 <仓库名/分支/commit>]  
> 核心结论置信度：[说明]  
> 未覆盖范围：[明确列出]

## 〇、大白话看懂（1 分钟建立全局）
- **一句话定位**：[谁在什么场景下解决什么问题，产出什么结果]
- **六个入门问题**：1) 谁用 2) 解决什么痛点 3) 什么触发 4) 怎么走完 5) 最终产出 6) 没有它会怎样
- **一个具体例子**：[标明示例值，按 业务意图 -> 系统能力 -> 证据锚点 串讲]

## 一、分析范围与覆盖账本
- 覆盖范围表 / 核心候选判断（附排除原因）

## 二、领域词典与核心模型
- 术语表（代码/原文名词 -> 业务含义 -> 生命周期角色 -> 证据）
- 核心关系（Mermaid `erDiagram` 或简洁关系表）

## 三、端到端全景、机制与「为什么」
- 全景图（Mermaid，先分析后生成，与证据一致）
- 核心流程拆解（步骤 | 触发/参与者 | 业务意义 | 数据/状态变化 | 失败与恢复 | 证据锚点）
- 关键状态机（仅写实际写入与守卫证实的转换）
- 核心业务规则与 6 类「为什么」深挖解析
- 异常、重试、超时与人工恢复矩阵
- [Doc/Hybrid] 核心图片/白板解读（每张 3-6 条）与图文交叉验证

## 四、架构演进与真实深水区
- 架构如何支撑业务（拒绝技术栈堆砌）
- **难点卡片（八要素）**：
  1) 业务场景与后果 2) 工程约束 3) 当前实现 4) 证据锚点
  5) 可确认保障 6) 权衡代价 7) 已知边界/风险 8) 若重做如何改进（标为 `工程评估`）
- **不应包装成亮点的部分**（普通框架用法、假实现、未落地机制、文档夸大）

## 五、证据地图、交叉对比与冲突待确认
- 结论 -> 证据标签 -> 精确锚点 -> 说明
- [Hybrid] 设计文档声明 vs 代码现实对比表
- 冲突项与待确认清单

## 六、面试表达与技术分享武器库
- **30 秒版本** / **2 分钟版本** / **10 分钟展开提纲**（方法模式用 一句话 / 1 分钟 / 深挖层）
- **新人技术分享脉络**（术语前置、演进因果链、无未经请求的比喻）
- **项目事实 vs 个人贡献措辞边界**
- **待补充真实指标清单**（指标 | 为什么会被问 | 可接受来源 | 当前状态）

## 七、分层追问树、自测题与掌握度地图
- 追问表（问题 | 安全答法 | 依赖证据 | 避免声称 | 二阶追问）
- 三轮自测题（回忆 / 原理解释 / 深挖实战，附强答案要点与证据锚点，初始状态 `待用户作答`）
- 掌握度地图（L1~L5，`已证明等级` 初始为 `待用户验证`）

## 八、反向完整性审计与未决项
- 审计核对清单 + 最终仍需业务方/运行环境/监控确认的事项
```
