# 教学内化、难点深挖与面试输出标准

无论是消化一篇架构长文、一个开源/业务仓库，还是单个核心方法，最终产物都必须把被动资料转化为读者**能看懂、能复述、能下钻、能扛住二阶追问**的可执行心智模型。

## 1. 因果模型重构（拒绝章节复读与技术栈堆砌）

绝不按原文章节顺序缩略改写，也不按代码目录树逐个类报流水账。所有知识统一重构为 **6 段因果链**：
1. **背景与约束**：谁在什么场景下使用？面临什么真实约束（规模、一致性、延迟、成本、合规）？
2. **旧方案为何失效**：基线方案或早期架构在什么约束下崩溃或遇到瓶颈？
3. **核心机制与架构**：当前设计如何精确回应上述约束（数据锚点、状态流转、编排链路、关键算法/协议）？
4. **演进决策**：关键技术转向为什么发生（原文/代码证实或显式标为 `交叉推断`）？
5. **权衡与条件化收益**：为了得到当前特性牺牲了什么？在什么前置条件下取得了什么效果？
6. **边界与失效模式**：结论在什么条件下不再成立？极端情况下如何降级与恢复？

## 2. 渐进式教学顺序（先教懂，再压缩话术）

在未建立稳固心智模型前，禁止提前生成面试包装话术：
1. **六个大白话入门问题**（禁止堆砌框架名词）：
   - 谁或什么系统使用它？
   - 它解决什么现实问题？
   - 什么事件启动它的主流程？
   - 一次完整业务从头到尾怎么走完？
   - 业务方或下游最终拿到什么结果？
   - 如果没有它，会出什么错、卡在哪或贵在哪？
2. **业务/领域词典**：把代码/原文术语映射为大白话含义与生命周期角色。
3. **一个具体场景串讲**：用一条贴合证据的示例贯穿主流程，每步拆清 `业务目的 -> 系统能力 -> 代码/原文锚点`（示例值显式标为示例）。
4. **灵魂「为什么」深挖（Explain Why）**：针对每条非直觉规则，必须追问并回答以下 6 类问题：
   - 为什么这个事件能触发主流程，而另一个相似事件不触发？
   - 为什么选用这个幂等键或状态守卫（而不是其他字段）？
   - 为什么这里采用快照读/冗余字段，而不是实时查最新数据？
   - 为什么这类失败设计为可重试，而另一类直接进入终态失败？
   - 为什么这个动作放进事务内（或刻意移出事务外）？
   - 当前设计用什么代价（复杂度/一致性延迟/存储）换取了现有特性？
5. **技术机制与证据锚点**：把理解落回具体文件行号、SQL 或原文图表块。
6. **权衡、短板与未决问题**。

**新人技术分享补充要求**：面向新人做技术分享时，必须先定义专有名词与前置条件，讲清系统演进的因果动力而非机械罗列版本号；**除非用户明确要求，否则不使用类比**，保持专业精准。

## 3. 真实深水区与亮点挖掘（八要素卡片）

每个站得住脚的难点/亮点，必须完整包含 8 个要素：
1. **业务场景与后果**（没处理好会引发什么真实业务事故）
2. **工程约束**（并发、一致性、外部不可靠、资源上限、复杂规则等）
3. **当前实现**
4. **代码或原文证据锚点**
5. **可确认的保障**（当前代码/方案确切能防住什么）
6. **权衡代价**
7. **已知边界或未解决风险**
8. **若重做的改进方向**（明确标为 `工程评估`，不冒充现状）

**反包装铁律**：普通框架常规用法（标准 CRUD、未处理一致性的 Redis 缓存、普通发 MQ）以及设计模式名词本身，属于实现词汇，不是难点。若项目确实没有深水区，如实说明，并保留假实现、死路径、文档与代码脱节等客观短板。

## 4. 面试表达武器库

仅基于已验证的心智模型生成以下口述与防御材料：

### 仓库 / 系统级口述版本
- **30 秒版本**：项目定位、解决的问题、核心结果、1 个差异化亮点。
- **2 分钟版本**：业务背景、代表性主流程、架构形态、2–3 个真实深水区挑战。
- **10 分钟展开提纲**：完整业务生命周期、核心模型与状态机、关键技术决策、异常与恢复、当前局限与反思。

### 方法级口述版本（`method` 模式）
- **一句话职责**
- **1 分钟串讲**：触发入口、校验规则、数据/状态变更、外部副作用、终态输出。
- **深挖层**：事务边界、幂等控制、并发冲突、异常恢复与代码锚点（局部追踪能支撑多少讲多少，绝不把单个方法吹成整仓架构）。

### 分层追问树
围绕核心流程与难点，覆盖：业务动机、实现深度、正确性与幂等、并发与规模、故障与恢复、诊断与可观测性、安全合规、权衡与备选方案、当前局限、演进重做。
每道追问必须给出：
- 安全简洁的标准答法
- 所依赖的已证实事实
- 禁止编造或越界声称的内容
- 面试官大概率接着抛出的**二阶追问**

### 项目知识 vs 个人贡献措辞隔离
深刻理解一个系统不等于必须由自己亲手从零写出。严格区分“知识深度”与“个人贡献事实”，推荐安全句式：
- 项目客观事实：`"这个项目里采用了……"` / `"系统目前通过……来保证……"`
- 展现深挖理解：`"这块的核心机制是……我展开讲一下。"`
- 用户明确确认亲自实现：`"这块由我设计/实现……"`
- 接手维护或后期深入梳理：`"这块不是最初由我实现，但我后来做了深入梳理/接手维护……"`

严禁从 Git 提交记录或仓库访问权限擅自推定个人贡献；未获用户确认一律标 `待确认`。

## 5. 掌握度体系、三轮自测与反馈闭环

### 掌握度等级
- `L1 看懂`（能说明白为谁解决什么问题）
- `L2 能复述`（不看代码/原文能讲清主流程）
- `L3 能解释`（能讲透规则、状态机与“为什么这么设计”）
- `L4 能下钻`（能准确定位关键类/表/状态写入/失败恢复点）
- `L5 能辩护`（能扛住权衡、边界、故障排查与重做方案追问）

核心流程目标 `L4`，核心深水区目标 `L5`；用户未完成作答前，`已证明等级` 默认写 **`待用户验证`**。

### 三轮自测题 + 6 步交互式反馈闭环
生成 **回忆题 / 原理解释题 / 深挖实战题** 三轮自测（附强答案必备要点与对应证据锚点，初始状态标 `待用户作答`）。当用户在对话中作答时，执行 6 步闭环：
1. 将用户回答逐条对照证据；
2. 指出遗漏的核心概念或没有证据支撑的说法；
3. 带用户回到对应的代码片段或原文图表位置；
4. 用大白话讲清认知缺口；
5. 抛出更深一层的追问继续验证；
6. 仅在用户实际答对后，更新对应主题的掌握度等级。

## 6. 绘图与一致性门禁

- 核心流程、数据锚点与状态稳定后再画全景图，放于档案靠前位置。
- 优先使用内联 Mermaid（`flowchart`、`sequenceDiagram`、`stateDiagram-v2`、`erDiagram`），使用项目/领域专属业务支柱命名，不用泛泛的“Controller/Service/DAO 分层图”敷衍。
- 若另行渲染 PNG/SVG：选用浅色易读背景，检查中文字符缺失/裁切/字体过小问题，并保留等价文字说明。
- **一致性门禁**：逐项核对图表节点、状态名、流向与异常分支是否与正文和代码完全一致。
